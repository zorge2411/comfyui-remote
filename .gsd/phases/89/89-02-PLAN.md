# Plan 89.2: Corpus Test Harness and Known-Failures Baseline

## Objective

Add a JVM unit test that converts every corpus fixture with `GraphToApiConverter.convert()` and runs structural checks C1–C7 on the output. Record today's failures in a known-failures list that the test enforces in both directions. After this plan, any converter change that breaks a working fixture fails the build, and fixing a known failure forces the list to be updated. See `89-CONTEXT.md` (D-05 to D-07).

**Depends on**: Plan 89.1 (fixtures and object_info.json)

    Put this in the test source set only; it is not app code. Add `ApiPromptValidator.validate(api: JsonObject, objectInfo: JsonObject, graph: JsonObject): List<Violation>`, where `Violation(check: String, nodeId: String, detail: String)` and `check` is "C1".."C7":
    - C1: `class_type` is missing from objectInfo.
    - C2: an input is a 2-element array `[String, Int]` whose node ID is missing from `api`, or whose slot is at least the length of the source type's `output`.
    - C3: the source `output[slot]` type is not compatible with the input's declared type. Compatible means equal, either side `*`, or overlap between comma-separated type lists. Skip inputs whose declared type is a combo (an array).
    - C4: an input under `input.required` is missing from `inputs`.
    - C5: a literal value for a combo input is not in its option list. Skip empty option lists.
    - C6: an ID of a graph node with `mode` 2 or 4 is present in `api`. Check top-level nodes only; subgraph-internal IDs are remapped.
    - C7: `class_type` is Reroute, PrimitiveNode, Note or MarkdownNote.
    Also add `ApiPromptValidatorTest` with small inline cases: one passing prompt, and one prompt per check C1–C7 that triggers exactly that check. This keeps the validator itself honest.
  </action>

    `WorkflowCorpusTest`:
    - Load `object_info.json` and every file in `workflows/` from the classpath (`javaClass.classLoader.getResource("workflow-corpus/...")`).
    - Call `GraphToApiConverter.convert(text, ComfyObjectInfo(objectInfo))` on each file, catching exceptions as check "C0" (the converter threw an exception).
    - Validate the output and collect the set of failing check IDs for each fixture.
    Compare against `known-failures.json`, whose format is `{ "<file>": { "checks": ["C7"], "reason": "...", "phase": 90 } }`:
    - An unlisted fixture with any violation is a regression.
    - A listed fixture whose failing checks differ from `checks` (including passing entirely) is a stale entry.
    - A listed file that doesn't exist is an error.
    Assert once at the end. The message lists every regression and stale entry, with the first 5 violations per fixture, so one run shows everything (D-07).
    Build the baseline:
    1. Run the test with an empty list.
    2. Investigate each failing fixture far enough to name the cause, e.g. "Reroute passthrough not type-aware" → phase 90, "missing-node list includes removed nodes" → phase 91. Anything that isn't a converter bug (a validator false positive) is fixed in the validator, not listed.
    3. Write `known-failures.json`.
    Do not change `GraphToApiConverter` in this phase. Do not use `@Ignore`.
    Finally, add a line to `MANIFEST.md` explaining how to update the known-failures list.
  </action>

  <done>The full suite passes with the baseline list. Two manual checks prove the harness bites: deleting a known-failures entry makes the test fail naming that fixture, and adding a bogus entry for a passing fixture makes it fail as a stale entry. Revert both afterwards.</done>
